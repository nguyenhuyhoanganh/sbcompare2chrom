Comparing two Chromium versions:
what changed, and how much it costs

Every uprev — moving onto a newer Chromium — someone has to answer two questions: what did Chromium change? and which of those changes are worth reading?

Running git diff between two versions produces several million lines, almost none of which answer either question. chromedrift takes a different route: it does not read the code, it reads only the declaration files — the places where Chromium lists what it has, in a machine-readable form — labels every difference with what it means, and ranks the labels.

This document walks the whole process, from two version numbers going in to the finished report coming out, and states plainly at the end what the tool cannot read.

First: what is a “feature”?

This section defines the words used in the eight stops that follow

“Feature X changed” sounds clear, but inside Chromium it is ambiguous, and that ambiguity is where most wrong conclusions come from. Take a real example: parallel downloading.

One feature a user can name is spread across several places

Where it lives in ChromiumWhat it isExample
Feature flag An on/off switch in C++ code, with a name and a default state ParallelDownloading
Feature param The tuning numbers that go with that flag min_slice_size, parallel_request_count
Pref Where Chromium stores the user's setting. Each pref is a key in the Preferences file inside the profile download.prompt_for_download
Control The UI element the user clicks on the Settings page: a toggle, a dropdown, a checkbox settings-toggle-button
chrome://flags entry Where a user can turn it on themselves, with the release it is due to be removed enable-parallel-downloading
What those five are — click for the explanations

Feature flag base_feature

A constant in C++ code with a name and a default state, on or off. When the code reaches a branching point it asks “is this flag on?” and takes the matching branch. This is also what Finch — Chromium's server-side experiment system — uses to turn a feature on for some percentage of users.

The real declaration of ParallelDownloading at M151:

// components/download/public/common/download_features.cc
BASE_FEATURE(kParallelDownloading,
#if BUILDFLAG(IS_ANDROID)
             base::FEATURE_ENABLED_BY_DEFAULT
#else
             base::FEATURE_DISABLED_BY_DEFAULT
#endif
);

Skim it and you see ENABLED and assume the feature is on. In fact that line is the Android branch; on Windows it falls into the #else, which is off. This is exactly the mistake that inverts a conclusion, and it is why stop 5 has to read the build condition around a declaration rather than taking the first value it finds.

Feature param feature_param

A number attached to one specific flag. The flag decides “is it on”; the param decides “once it is on, with what settings”: thresholds, timeouts, sampling rates, retry counts.

A param the tool reads at M151:

flag  DownloadWarningSurvey
param ignore_delay_seconds = 300

Changing 300 to 30 is a real behaviour change — but the flag's state has not moved, so watching flags alone shows nothing. That is why params are a fact kind of their own.

An honest note on coverage. The two params in the example column above — min_slice_size and parallel_request_count — belong to ParallelDownloading itself, but they live in a file the current fetch list does not reach, so the tool cannot read them. That is precisely the kind of gap the chromedrift catalog command exists to measure, and why the end of this document states coverage rather than staying quiet about it.

Pref pref

A user setting. Chromium does not keep these in the registry or a database, but in a JSON file called Preferences inside the profile directory. For Chrome on Windows that is …\User Data\Default\Preferences.

The dots in a pref name are the path into that JSON file. download.prompt_for_download means: go into the download object, take the prompt_for_download key. 

// the Preferences file in a user's profile
{
  "download": {
    "prompt_for_download": true,
    "default_directory": "C:\\Users\\me\\Downloads"
  }
}

And in the source, that key is declared as a constant:

// chrome/common/pref_names.h:416
inline constexpr char kPromptForDownload[] = "download.prompt_for_download";
//         ^ C++ variable, stable      ^ THE STRING, which is the identity

Telling those two apart matters. If Chromium changes the string and keeps the variable: the code still builds (everything goes through the variable), the tests still pass (they use the variable too) — but on the user's machine, Chromium looks for the new key in Preferences, does not find it, and uses the default. Every existing user's setting quietly resets, without a single error line.

Control webui_control

The UI element a user can click on a chrome:// page: a toggle, a dropdown, a checkbox, a button. These pages are real web pages, so controls are declared in HTML files.

The “Ask where to save each file before downloading” toggle, as really declared at M151:

// chrome/browser/resources/settings/downloads_page/downloads_page.html:31
<settings-toggle-button
    pref="{{prefs.download.prompt_for_download}}"
    label="$i18n{promptForDownload}">

Two things are worth noting. First, the control's type is the tag name — so a dropdown turning into a toggle is detectable automatically, without looking at a screenshot. Second, the pref= attribute links the control straight to the pref underneath it; that is the strongest declared link between the UI and the browser core, and it survives a redesign of the page, because the pref underneath does not change.

chrome://flags entry flag_entry

chrome://flags is the page where users can try out unreleased features themselves. Every entry on it has a record in flag-metadata.json, and that record holds something no other source has: the release the flag is due to be removed in. 

// chrome/browser/flag-metadata.json
{ "name": "enable-parallel-downloading",
  "owners": ["qinmin@chromium.org", "xingliu@chromium.org"],
  "expiry_milestone": -1 }   // -1 = no removal date

This is the only source in the tree that talks about the future rather than the present. Because of it, "twelve flags we depend on will be removed at M151" becomes something you can plan for today, instead of a build failure discovered at the next uprev.

Those five rows are five separate declarations, in five different files. No file in Chromium says “parallel downloading consists of these five things”. The tool reads each declaration on its own; assembling them into a feature a user can name is the reader's job, not the tool's.

Four words used throughout this document

The four words below are the real names of the four data stages inside the tool — you will meet exactly these words again in report.json. The examples are the real change running on the belt above.

factone declaration
One declaration, read out and normalized into data. At M148 the tool read: name GlicActorUiMagicCursor, state on Windows is off. At M151 the same declaration says on. An M151 snapshot with the default target set produces about 24,960 facts.
changea difference
Put two facts with the same name from two versions side by side and record where they differ: state on Windows: off → on. Every fact kind has a fixed list of attributes the tool compares — an attribute outside that list can move without counting as a change.
signalwhat it means
The label explaining what that difference means, and the severity it carries. Here: “default flipped on for Windows”, severity 75. A change can carry several signals; the heaviest one is the leading signal, and it sets both the severity and the bucket.
findingranked, and filed
A change plus a score and a bucket. The declaration is in the Windows build and this is not a removal, so nothing is deducted: the score stays at 75 and it is filed under Behaviour change. This is what appears in the report.

Three kinds of change

Every difference is one of three, and what each one means is not symmetric — the third is the only one seen from both sides.

KindLiterallyWhat it means
added Present on the right, absent on the left Chromium added it. New surface — nothing is switched on by it on its own.
removed Present on the left, absent on the right Chromium removed it — or moved it into a file this run never opened. Which of those it is depends on how much of the tree was read, and the score says so.
modified Same name, different value Chromium changed the value. If it is a default state, users see something different.
A removal is an inference from absence, and the other two are not. Both sides of a modification were read; an addition is a thing seen. A removal is a thing not seen, which on a run covering 5% of the tree is a much weaker claim than on one covering all of it. Measured M148 → M151: of 141 preference keys that vanished, 100 had simply moved into a file the run never opened.

The four buckets in the report

Every finding lands in one bucket, and the bucket is decided by the leading signal — the same one that set the severity. So a row is filed under the sentence it was ranked by, rather than under a sentence chosen separately from the ranking.

BucketMeansHow to read it
Breaking Something outside the binary stops working, silently: stored user data, launch scripts, Finch configs, live websites, the other process Find every place that names it
Behaviour change The Windows build behaves differently. Someone can see a difference Confirm what the difference is
New surface Surface that did not exist before. Nothing is switched on by it on its own Input to a product decision, not a risk
Housekeeping Chromium tidying up after itself, and scheduling. Nothing observable moved, or the tool cannot tell that anything did Do not read line by line
A retired flag is Housekeeping, and that is the most consequential row in the table. M148 → M151 removes 90 base::Feature flags, split exactly 45 that shipped and 45 that were abandoned, and not one of them changes what a user sees. Filed as breakage they are 90 rows at the top of the report of which none is actionable — which is how a triage tool becomes one people stop opening. The label still says the switch is gone.
One bucket moves with the coverage, deliberately. pref_left_scan means “deleted, or moved out of the files we read”, and which of those it is depends entirely on how much of the tree the run covered. On --target-set default (5% of files) 139 of these are filed under Housekeeping at 20 points; on wide (100%) 171 are filed under Breaking at 35. A rule that gave the same answer either way would be wrong in one of the two directions.

And a third axis: whose desk it lands on

The bucket says how bad and the consequence group says what kind of consequence. Neither says whether a row is yours, and a 3,000-row report is read by several people who each own a fifth of it. So the same leading signal that set the score and the bucket also routes the finding to one of five owners.

The last two columns point opposite ways, which is the whole reason to split. The longest list carries two of the 315 Breaking rows; the second shortest carries 126. Routing is by surface except where the fix is somewhere else than the declaration: a renamed C++ constant stops the build and is fixed in the file beside it, while a renamed Finch string compiles perfectly and is fixed in a server-side config nobody can see from this repository. Eight signals override their surface for that reason and route to Outside the repository — the owner that owns no files, and where the silent failures collect.

One table, and every row says what it is

The four buckets above are the reading order, not a severity order — a Housekeeping row can outscore a New surface one. report.html is a single table, filterable and sortable. Two other layouts were tried on top of it and both were worse — recorded here so nobody goes back.

Grouping every finding by signal on one long scrolling page. It became twenty-one collapsed bars whose titles are near-synonyms in Chromium's own vocabulary — Default flipped on, Now ON by default on Windows, New feature, on by default are three different entries — eighty bars, three levels deep, before the reader reaches one readable row.

Putting those behind a per-team menu. The accordion wall went away, and so did the one thing a table is good for: seeing everything at once, sorting it, searching it.

What was missing was never the shape. It was that a row said id:cancelButton and left the reader to guess: which page, added or removed, what kind of control, and what happened to it. So the table keeps its shape, and every row now carries the answer.

Pinning the version

acquire.py · the resolve_ref function

The tool accepts three kinds of input and handles each differently.

InputHow it is handledResult
151.0.7922.138 A full version number, used directly refs/tags/151.0.7922.138
151 A bare milestone number; the tool asks the chromiumdash service for the newest stable release of that milestone changes with the day you run it
main/dev Matches neither of the above, passed straight to Git main/dev
Use full version numbers for anything official. A bare milestone resolves to the newest stable release at the moment you run it, so two runs a few weeks apart can produce two different conclusions and both are correct. A case we hit: the ServiceWorkerAutoPreload flag is on in 143.0.7499.40 but off in 143.0.7499.194 — the same milestone, a different patch release, because the change was reverted.

Fetching the declaration files

targets.py · acquire.py

Syncing a full Chromium costs about 100 GB and several hours per version. The tool does not need all the source, only the declaration files, so it fetches individual directories as archives straight from the Gitiles server and unpacks them into a directory tree that looks like Chromium but holds a few thousand files.

About 40 MB per version. The first run takes over a minute; later runs read from the cache and are nearly instant. --target-set wide downloads 337 MB and keeps 102 MB on disk, and in exchange reads every declaration file in the tree instead of 4%. Every run measures and prints its own number, so this is a measurement taken at M151, not a constant.

The cache records the outcome of each fetch, not merely that one happened. A file legitimately missing from an older version is normal, so the cache records that case too. But it has to record “fetched” or “not there”, not just “done”. Because with only “done”: a first run where every fetch failed reports an error, and then the second, identical run reads the cache, sees “done” everywhere, believes it succeeded, and writes out a snapshot with nothing in it.
4

Nine sources of data

Each source answers a different question about an uprev

The nine sources below were chosen by exactly one criterion: they are the places Chromium is obliged to declare what it has, in machine-readable form. Some are inputs to a code generator, so they cannot be wrong; the rest follow conventions that have been stable for years. That is what lets the tool read them without a compiler and without a full Chromium checkout.

Each source is described the same four ways: what the file contains, its role in Chromium, what the tool compares, and the consequence of missing it.

Group A — flags that control behaviour

Three sources decide what users actually get. A change here is a behaviour change, even when not a single line of logic was edited.

Flag declarations in .cc files flag
ContainsFlag declarations in C++. Each flag has a name and a default state: on or off.
RoleThis is Chromium's runtime feature-flag system. Almost every meaningful behaviour change sits behind a flag. Finch — Chromium's server-side experiment system — also turns things on and off per user group through these same flags.
Compared byPaired by normalized flag name. The compared value is the default state that applies to the Windows build, together with the build condition around the declaration.
Missing it meansNot knowing which feature was just turned on for our users. A default moving from off to on is how Chromium announces that a feature shipped, and that information does not appear in the release notes.
The parameters attached to a flag flag
ContainsParameters tied to one specific flag: thresholds, timeouts, sampling rates, retry counts.
RoleThey allow behaviour to be tuned without turning the flag on or off. The flag's state does not move; only the number inside changes.
Compared byPaired by the owning flag plus the parameter name. The compared value is the default.
Missing it meansSkipping an entire class of behaviour change that comes with no flag-state change at all. Dropping a timeout from 2,000 milliseconds to 500 is a real change for users while every flag stays exactly as it was.
runtime_enabled_features.json5 flag
ContainsThe manifest of every web-platform feature, each with its release status: stable, experimental or test, declarable per platform.
RoleA complete, machine-readable list of every web API Chromium has. It is the one source the tool covers completely, because the whole list is one file.
Compared byPaired by feature name. The compared value is the release status on Windows.
Missing it meansNot knowing which API is about to become visible to real users. Moving from experimental to stable means websites will start using it.

Group B — contracts with the outside world

Four sources describe what Chromium promises the world outside it: websites, launch scripts, stored data, and other processes. What they have in common is that breaking the contract does not break the build.

pref_names.h — pref declarations contract
ContainsString constants naming each user pref.
RoleEvery pref is a real key in the Preferences file inside the user's profile. It is also where enterprise policy and the Settings page write.
Compared byIdentity is the key string, not the variable name. The C++ variable is used to pair a removal with an addition, so a rename can be recognised.
Missing it meansMissing a class of breakage that leaves no trace at all. Renaming a key orphans every existing user's stored value: the code still builds, the tests still pass, and the user's setting quietly reverts to the default.
*_switches.cc — command-line switches contract
ContainsString constants naming each command-line switch.
RoleA contract with things outside the browser's source: launch scripts, test automation, device configuration.
Compared byIdentity is the switch string, with the same rename detection as prefs.
Missing it meansRenaming a switch produces an error nowhere. The script still runs, the switch simply stops taking effect. No compiler can catch it, because the user of it lives outside the repository.
*.idl — web API definitions contract with websites
ContainsThe definition of every web API exposed to JavaScript: interface names, member lists, and each member's signature.
RoleChromium generates its bindings straight from these files. They do not describe the API — they are the API.
Compared byPaired by interface name plus member name. The compared value is the full signature and its extended attributes.
Missing it meansLosing the only source that can identify an API being removed. A member disappearing means live websites break. Note that a Blink flag disappearing is not a signal of this — see the three-stage lifecycle at stop 6.
*.mojom — Mojo, how processes call each other internal contract
ContainsMojo interface definitions: method names, parameter lists, return values.
RoleMojo is how Chromium's processes call each other — browser, renderer, GPU, network. The bindings on both ends are generated from these files.
Compared byPaired by the method's fully qualified name. The compared value is the whole signature, so a parameter changing type or order is caught.
Missing it meansMissing the most severe class of change. Changing a Mojo method's signature breaks at runtime, not at build time, because the two ends live in different processes and each generates its own bindings. No web test catches it.

Group C — the UI and the schedule

The last two sources describe what users see, and what Chromium plans to remove in future.

The three files of a chrome:// page UI
Containschrome://settings, chrome://history and chrome://downloads are all web pages built from the same three-file pattern: a route table listing the sub-pages with their gates; a template declaring each control; a C++ handler turning flag values into variables JavaScript can read.
RoleThe three files form a three-hop chain: route → gate → feature flag. Only by walking the whole chain can you answer “why did this page disappear”.
Compared byFor a route: its path, its parent route, and its gate. For a control: the HTML tag (so a dropdown turning into a toggle is caught automatically), the pref it writes, and its label. For a handler: the flag expression that decides the value.
Missing it meansNot detecting UI changes at all. All three files have to be read: a route table also lists pages a flag is currently hiding, so stopping at the first file gives a conclusion opposite to reality.
flag-metadata.json — the removal schedule schedule
ContainsMetadata for each chrome://flags entry, including the milestone it is scheduled for removal in.
RoleThe only source in the tree that talks about the future rather than the present.
Compared byThe removal milestone. A flag whose removal date falls on the version being adopted, or just after it, is marked.
Missing it meansLosing the ability to plan. "Twelve flags we depend on will be removed at M151" is something you can schedule today, instead of a build failure discovered at the next uprev.
Why only these nine. What they share is that they are obligatory: API definitions and Mojo definitions are code-generator inputs, so they cannot diverge from reality; the web-platform manifest is a configuration file; and flag declarations and C++ string constants follow conventions that have held for years. By contrast, the logic inside a function body describes nothing, so it is outside the tool's scope. That is a limit stated plainly at the end of this document, not one hidden away.
5

Reading files into facts

extract/ · nine extractors, one per kind of file

The tool has no compiler and no full Chromium checkout. But the declarations it needs all follow writing conventions that have been stable for years, so pattern scanning — recognising those exact shapes — is accurate enough without full syntactic parsing. The part that has to be exactly right is the condition around the declaration.

How each kind of file is compared

Comparing has two steps. Step one, pairing: work out which declaration in the old version corresponds to which in the new one — what you pair on is called identity. Step two, comparing the values of the pair you just matched. Choosing the wrong identity is the most damaging mistake: pair wrongly and every declaration looks as though it was just deleted and re-added.

Kind of file The identity used to pair The values compared

Identity has to survive a change of syntax

Between M139 and M143, Chromium changed the very macro used to declare a flag: the argument holding the flag's name was dropped, and the name is now derived from the variable name. Not one flag changed its name, its state or its behaviour — only how it is written.

In one measured file, M139 has 170 of 170 declarations in the old form, while M143 has only 12 of 187. A tool taking identity from the source text would report that the entire file had just been rewritten. After normalizing the variable name into the flag name, the real difference is 152 unchanged, 18 removed, 35 added.

The build condition decides which value gets read

One flag can carry several different default states inside a single declaration, selected by the platform being built: on for desktop, off for mobile, or the reverse. Taking the first value you find is wrong, because if the Windows branch is not first, the conclusion is exactly backwards rather than merely imprecise. In one measured file, 14 of 187 flags have per-platform defaults.

The tool reads the condition around the declaration and picks the branch that applies to Windows. The result is one of three states:

The condition depends onResultWhat the tool records
The platform we ship Applies The value in that branch
A different platform Does not apply That branch is skipped, or recorded as not compiled if the declaration exists only there
A build flag unrelated to platform Undecidable “Undecidable” — the tool picks no branch
The third state is the important one. When the condition depends on a parameter that enables or disables an optional component, the tool does not have enough data to decide. It records “undecidable” rather than picking a branch, because a wrong value looks exactly like a right one, whereas “undecidable” tells the reader immediately that they need to check.

Comparing two versions

diff.py

The two rules below do most of the narrowing. The first throws away differences that say nothing. The second explains why most of what looks like a lost feature is not a lost feature.

Rule 1 — compare only the attributes that actually mean something

Every fact kind has a fixed list of attributes the tool compares. An attribute outside that list can move as much as it likes without counting as a change. The panel below puts two versions of the same flag side by side. Pick a scenario to see which attributes are compared and how the conclusion follows.

Pressing “Only the syntax changes” shows this rule most clearly. The two versions differ in the attribute recording the declaration form, but that attribute is not on the compared list, so the conclusion is no change at all — which matches reality. Had the tool compared it, the macro migration between M139 and M143 alone would have produced thousands of “changes”, not one of them worth reading.

Rule 2 — the three-stage lifecycle

Chromium moves every feature through three stages, usually several milestones apart. The consequence is that a comparison between two versions mostly sees stage A and stage C, while stage B is when users actually notice a difference.

StageWhat happens in the sourceWhat users see
ANew code is added, flag defaults offnothing
BThe flag flips onthis is the change
CThe old code path and the flag are deletednothing

So when a flag disappears, the tool reads the state it held immediately before removal. A flag removed while on means the feature shipped earlier and can now no longer be turned off; a flag removed while off means the feature never shipped and the code has been deleted. Those two are completely different, and neither is a lost feature.

Measured on M148 → M151, Windows: 90 flags removed, splitting exactly 45 and 45 between the two cases above. Labelling all 90 “feature lost” makes half the list a false alarm. For web-platform features it is starker still: 202 entries disappeared, of which 170 were in stable — cleanup after shipping, not an API removal.

The hardest case to spot: a rename

For prefs, command-line switches and flag names, identity is a string, while the C++ variable name is stable. So a rename shows up in the results as one item removed plus one item added, two entries that look unrelated, with the real consequence hidden between them.

A case we hit: the macro migration between M139 and M143 changed a flag's name from FedCmIdPregistration to FedCmIdPRegistration — one letter's case. Nobody edited the name; changing how the macro is written changed it. From then on, every server-side experiment config and every command-line switch written the old way silently stopped working, and no compiler warned about it.

The tool pairs a removal with an addition when they share the same C++ variable name, and reports the pair as one rename rather than two unrelated events.

7

Ranking

diff.py · score.py

Two numbers travel with every finding, and the gap between them is the point. Severity is what this kind of change costs. Score is that after two facts about this particular run.

Severity comes from the leading signal — the label with the highest weight among the ones the comparison attached. Only when a change carries no signal at all does it fall back to a coarse guess from the kind and the direction. That order is the whole design: the signal is a statement about what happened, the guess is a guess, and it used to be max(guess, signal) — so the guess overrode the statement exactly when the statement was lower, which is where the guess was wrong.

Measured against two real pairs of versions, the guess overrode the signal on 267 of 2,800 findings at M148 → M151 and 345 of 6,787 at M143 → M151 — every one of them upwards.

The two deductions

Nothing raises a score. Severity is the ceiling — the most this kind of change can cost — and each deduction below it arrives with a sentence attached to the finding. Turn them on to see the score and the bucket move.

“Both sides” carries the whole first rule. A declaration that enters or leaves the Windows build keeps its full severity, because that is the change. The previous version read only the new side, so a feature whose Windows guard closed — the case where the feature is lost — was scored down 45 points for not being in the Windows build.
The bucket does not come from the score. It comes from the leading signal, the same one that set the severity, so a row is filed under the sentence it was ranked by. The one exception is above: an unconfirmed disappearance moves to Housekeeping, because on a partial read that is what it is.

Where the severity comes from

No severity is typed in by hand for a particular change. Every signal carries one, and a change takes the severity of the heaviest signal it received — the leading signal, which also decides its bucket.

SignalMinimumWhy it sits there
Default flipped on for Windows75Our users get different behaviour
Global default flipped on60May not apply to Windows; needs checking
Flag deleted, prior state unreadable65Not enough data to classify; someone has to look it up
Flag retired after shipping35Behaviour does not change in this uprev
Flag retired without ever shipping30The code is gone; it cannot be turned back on
A Mojo method's signature changed80The highest in the system: it breaks at runtime, across a process boundary
Note the gap between the first two rows. The first says what our users get; the second says what Chromium wrote in the source. Those two frequently disagree, and only the first deserves to be called a behaviour change.
Every point of difference between the severity and the score is recorded with a readable reason on the finding itself, because a ranking that cannot be argued with is a ranking that gets ignored the first time it is wrong. Both documents quote those sentences, and a test holds the quotes to strings the code actually emits — that pair drifted within an hour of being written.
8

Gathering scattered items back into one change

cluster.py

A single change in Chromium usually leaves traces in several different sources, and therefore appears in the report as several separate items. Read individually, they contradict each other: one says a page was removed, the next says a page appeared.

The real example is the local-network permission migration between M148 and M151. It produces seven findings across five fact kinds: two routes, two gates, one control, one feature flag and one web-platform feature.

Fact kindNameRecorded as
Page routeSITE_SETTINGS_LOCAL_NETWORK_ACCESSremoved
Page routeSITE_SETTINGS_LOCAL_NETWORKgate changed
Visibility gateenableLocalNetworkAccessSplitPermissionsremoved
Visibility gateenableLocalNetworkAccessSettingexpression changed
ControlsiteSettingsLocalNetworkAccessremoved
Feature flagLocalNetworkAccessChecksSplitPermissionsretired after shipping
Web-platform featureLocalNetworkAccessSplitPermissionsdropped

Grouping is based on the links the data itself declares, not on how similar the names look: a route names its gate, a gate names the flag it reads, a web-platform feature declares its matching C++ flag. Because those links are facts rather than guesses, the resulting group is exact, not approximate.

Read as one group, those seven items say something single and simple: the permission page moved to the split-permission mechanism, users have been seeing this since M148 because the matching flag was already on then, and the only thing to do is update one stale route reference.
9

The report

report/markdown.py · report/html.py

The process ends at the report. The tool does not conclude what a change means for any particular product: that takes judgement about a codebase this tool has never seen, and it belongs to the reader. So every finding carries its score reasoning and the line that declares it on each side — enough for the reader to reach their own conclusion, and to argue back if they think it is wrong.

Three output formats

report.md — paste straight into a ticket or a wiki.
report.html — sectioned by the questions a reader arrives with, with a final table that filters and sorts, and no external resources, so it opens on an isolated network and can be attached to an email.
report.json — for scripts and for comparing across uprevs.

Everything is analysed; nothing is cut

The JSON always holds every finding, Housekeeping included, and the two rendered files are views of it. Narrowing before the analysis is how a report loses its top: the most severe items are usually shared plumbing — Mojo signature changes — which belongs to no product feature and is the first thing any product-shaped filter drops.

report.md gives a table to Breaking, Behaviour change and New surface, and deliberately none to Housekeeping: it is the largest bucket in every report and the one nothing in it needs doing about. It is still in report.json and still in the sortable table in report.html — printed, not omitted, just not printed first.

Verification and limits

Coverage was measured on the Settings page between M143 and M148, against a reference set built separately by grepping the source with regexes — going nowhere near the tool's own extractors, so that the two could not be wrong in the same way.

10/10
routes
7 added · 3 removed
48/48

34 added · 14 removed
40/40
controls with a pref
19 added · 21 removed
Two numbers moved during the measurement, in opposite directions. The reference set reported three missing gates, and all three were errors in the reference: its regexes read line by line, so they missed calls written across several lines, which the tool's bracket counter handles correctly. But the reference also found one real bug in the tool: a control's identity was then based on its pref alone, and prefs are not unique — 142 of 881 elements were being swallowed, and which one survived depended on directory walk order. Fixed by adding the element's id to the identity.

What the tool does not read

Not readConsequence
C++ function bodiesLogic changing inside a function is invisible to the tool
A page's TypeScript logicOnly the declarative part of a template is read, not the page's behaviour
Display strings in .grd filesRelabelling a Settings entry is a user-visible change, and the tool does not detect it
CSS, layout, iconsNo screenshots, no visual regression detection
The build configuration (GN)A declaration existing in the tree does not mean it is compiled into the shipped binary

Coverage depends on the target set, and every run prints the number it measured. At M151, default reads 64 of the 1,164 files that could declare something (5%) but still captures more than half the base::Feature declarations, because the hand-picked files are the largest ones. --target-set wide reads all 1,164. That figure once said 100% while reading 87%, because the denominator was the roots the fetch list lived under rather than the tree; it is now the tree, and the roots the measurement named have been fetched. For surfaces like prefs, switches and Mojo the gap between the two target sets is very large — prefs 689 against 2,460, Mojo interfaces 338 against 1,501 — so when the answer really matters, run wide.

So Breaking: 0 never means “this uprev carries no risk”. It means “nothing was found within the scope that was scanned” — and on the default set an unconfirmed disappearance is filed under Housekeeping by design, so some of what would be breaking is not counted there at all. Every report should restate the coverage figure the run printed.
Every figure in this document was measured against real Chromium source (M139, M143, M148, M151) and can be reproduced with chromedrift catalog and chromedrift run.
